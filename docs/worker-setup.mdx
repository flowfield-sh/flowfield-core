---
title: Project setup and checks
description: Configure repository setup, meaningful checks and local result previews.
---

Before running tasks, configure each project's **Project settings**, directly or with the Coordinator. Use the repository's existing scripts and a committed baseline.

| Setting | Purpose | Example |
| --- | --- | --- |
| Destination branch | Local branch where approved code is delivered. | `main` |
| Setup commands | Install dependencies in fresh worktrees. | `pnpm install --frozen-lockfile` |
| Validation commands | Check the proposed code before approval. | `pnpm test` |
| Run command | Launcher for **Run result**, configured before code work starts. | `pnpm dev` |

For libraries or other projects without an interactive or command-line preview, choose **Execution → No runnable result** and record why. Code work waits until this choice is saved; report-only work does not require it.

Delivery starts with the repository’s current branch. Saving the initial Delivery, Setup or Validation settings records that default; later checkout switches do not redirect delivery. Saving a new destination branch name creates it from the repository’s current commit.

Enter one shell command per line for setup and validation. Choose commands appropriate to your repository; the service host must already provide the language tools and credentials.

Validation commands are optional and can be cleared. Results state when none are configured.

Flowfield refreshes tracked upstream branches before work and delivery. Local changes, divergent history or access failures appear as blockers; running attempts keep their starting commits.

## Validate before running workers

1. Commit setup scripts, manifests and relevant repository guidance to the destination branch. Commit or ignore adoption metadata under your repository's rules; untracked files can block delivery.
2. Save each tab. In **Setup**, **Validate** runs setup alone in a fresh copy. In **Validation**, **Validate** runs saved setup followed by validation commands. Progress and results appear below the buttons; no model or queue starts.
3. Choose a worker harness and model in **Workspace settings → Workers**, with supported effort/access controls. Capacity defaults to five parallel workers; adjust it to suit your projects.
4. Have the Coordinator create a task, move it to **Up next** and choose **Run queue**.

Setup and checks run in the worktree directory and must leave source files unchanged. Keep dependency outputs ignored; use `FLOWFIELD_RUNTIME_DIR` for temporary files and `FLOWFIELD_WORKSPACE` for the checkout path. Checks must finish and return a failing exit code on failure. A development server belongs in Run command, not validation.

If validation fails, fix the reported problem and validate again. Revalidate after changing setup, checks or the destination branch.

## Checks that need services

Use a test script that starts disposable services, waits for readiness, runs checks and cleans up on success, failure or interruption. Keep the entire lifecycle within the timeout.

Each command runs in a separate shell and its child processes stop when it finishes. Use an agreed external service for anything needed throughout the worker session; do not detach services from setup or checks.

For a shared service, agree its endpoint, data permissions, version and owner. Workers must leave borrowed services running. Cross-project references supply evidence, not running services.

## Saved checks during development

Workers can run the saved validation commands through Flowfield by default. The commands are frozen for each attempt, execute on its managed copy and retain output automatically. [Saved project checks](/configuration#saved-project-checks) explains their scope.

For repeatable browser checks, include a repository-owned headless browser script in the saved validation commands. Workers can run that script through `run_project_checks` with Flowfield host access, without repeatedly requesting the same native browser operation. Install its dependencies through Setup and isolate its profile, ports and data. Ad hoc native checks still follow the harness’s permissions.

Setup scripts can use `FLOWFIELD_CACHE_DIR` for package/download caches shared by the same repository in this Flowfield store. For example, `npm ci --cache "$FLOWFIELD_CACHE_DIR/npm"` reuses downloads while installing into each fresh checkout. Use tool/lockfile keys and concurrency-safe cache tooling. Keep builds, application data, credentials and test evidence out of this cache. Cache contents survive service restarts; setup and validation still run. Workers and Reviewers receive observed service tool paths and runtime/cache locations; these observations do not prove native browser or display access.

Saved checks retain their logs with the attempt. Workers and Reviewers can inspect that evidence, and you can read the command output when reviewing the result.

## Choose workers

Set workspace defaults or use **Task settings → Worker** to override them. Changes apply to the next attempt.

Fast is off by default; enable it in Worker or Reviewer settings when supported. See [Agent setup](/agents/overview) for supported controls.

For concurrent tasks, configure separate ports, databases and other mutable resources. See [project execution](/configuration#project-execution) for where commands run.

## Try a result

Open a prepared code result and choose **Run result** in its status notice. If automatic preparation is disabled, or Flowfield has restarted, choose **Prepare** first. Flowfield prepares an independent copy of that exact candidate, runs the saved setup commands, and owns the run command and its child processes. Opening the result page executes nothing.

**Prepare new results automatically** is on by default in **Execution**. Turn it off to prepare each result manually. Give long-running services a **Readiness command** that exits successfully when usable; batch commands should finish and leave readiness empty. The execution check time limit is independent of validation commands. A Worker can provide a URL in its result recipe to show **Open result**; project settings have no URL field.

For a batch tool, save a command with its sample inputs and leave the URL empty. A successful exit shows **Finished**; output remains readable and **Run result** can repeat it. Commands run without an interactive terminal and receive closed standard input, so supply arguments or pipe sample input explicitly. A desktop application can run its foreground executable directly; it appears on the service host, which may be different from your browser's computer.

Keep the run command and its services in the foreground. A repository script can start several related services and wait for them. Commands that daemonize or hand off to an existing desktop application are outside managed cleanup. Use separate ports, databases and sample data for each task; Local execution uses the service host and is not a security sandbox.

For several services, the launcher must stop the others and exit unsuccessfully when a required service fails. Check all required services for readiness, including an identity or private marker that distinguishes this run from another process on the same port. Put generated reports in `FLOWFIELD_OUTPUT_DIR` and builds/cache files in `FLOWFIELD_RUNTIME_DIR` or ignored project paths; modifying source files during setup prevents the prepared copy from running. Result environments provide a short private temporary path for tools that use Unix sockets. Use `$FLOWFIELD_PORT` in commands and `${FLOWFIELD_PORT}` in the recipe URL for an allocated local port. The application must bind it; Flowfield never stops another process to free a port.

Project settings supply defaults; each Worker can submit a structured `recipe` with result-specific setup, run, readiness, URL and generated-file selections. Flowfield freezes the resolved recipe with that result. Editing project defaults affects future results, including corrections, without changing earlier results. Workers receive the complete frozen defaults and a comparison with the previous effective recipe. Corrections explicitly resubmit still-needed overrides, including URLs and generated-file selections; omitted fields use the current defaults.

Before independent review, Flowfield verifies the saved recipe on a separate candidate copy: prepare, run to readiness or completion, stop, confirm cleanup, and run again with retained runtime files. A failing recipe blocks review with evidence for the existing correction loop. This checks execution and repeatability; the Reviewer still evaluates the task outcome.

The Worker selects result-specific paths in `recipe.outputs`, relative to `FLOWFIELD_OUTPUT_DIR`, to retain files when a run finishes or stops. There is no project-wide generated-files setting. Open them from the result notice or **Files**. Each run captures new immutable files; earlier files stay available. These are run outputs, separate from files submitted as the task delivery.

Each task has one active result runtime. **Stop** ends its processes while preserving the prepared copy, saved files and logs. Choose **Run result** to start it again during the same Flowfield session. Requesting changes stops the old runtime before correction work begins. Feedback uses the existing **Request changes** action and stays bound to the result you tried.

Flowfield stops its owned result processes when it shuts down or restarts. Return to the result and choose **Prepare again** to run it in the new service session. Existing dependencies and builds can be reused; preparation does not reset local edits. If a copy has edits, preparing again creates another copy and preserves the old one. Runtime edits never change the candidate used for approval.

Runtime failures appear in the result notice. Choose **Result output** for scrollable output and a log download, then use Back to return to the result. Logs indicate when their size limit was reached. If cleanup is uncertain, inspect and stop the remaining processes before choosing **Confirm stopped**.
