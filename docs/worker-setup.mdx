Before running tasks, configure each project's **Project settings → Integration**, directly or with the Coordinator. Use the repository's existing scripts and a committed baseline.

| Setting | Purpose | Example |
| --- | --- | --- |
| Destination branch | Existing local branch where approved code is delivered. | `main` |
| Setup commands | Install dependencies in fresh worktrees. | `pnpm install --frozen-lockfile` |
| Validation commands | Check the proposed code before approval. | `pnpm test` |
| Run command | Optional launcher for **Run result**. | `pnpm dev` |

Enter one shell command per line for setup and validation. Choose commands appropriate to your repository; the service host must already provide the language tools and credentials.

Validation commands are optional and can be cleared. Results state when none are configured.

When the destination tracks an upstream branch, Flowfield fetches it and fast-forwards the clean destination before starting new work. Running attempts keep their saved commits. Result preparation and delivery also check upstream, so changed code receives fresh validation and approval. Branches without an upstream remain local. Routine refresh needs no action; unavailable access, divergent history or local checkout changes appear as specific blockers without discarding work.

## Validate before running workers

1. Commit setup scripts, manifests and relevant repository guidance to the destination branch. Commit or ignore adoption metadata under your repository's rules; untracked files can block delivery.
2. Save Integration settings and choose **Validate setup**. Flowfield checks the saved branch in a fresh worktree, runs setup and validation and reports readiness.
3. Choose a worker harness and model in **Workspace settings → Workers**, with supported effort/access controls. Capacity defaults to five parallel workers; adjust it to suit your projects.
4. Have the Coordinator prepare a task, move it to **Up next** and choose **Run queue**.

Setup and checks run in the worktree directory and must leave source files unchanged. Keep dependency outputs ignored; use `FLOWFIELD_RUNTIME_DIR` for temporary files and `FLOWFIELD_WORKSPACE` for the checkout path. Checks must finish and return a failing exit code on failure. A development server belongs in Run command, not validation.

Read failed validation output, fix the scripts or configuration and validate again. Revalidate after changing setup, checks or the destination branch. Setup and validation commands have configured timeouts. Follow an active worker in its [task feed](/tasks#follow-an-attempt), and ask the Coordinator to stop it when needed.

Ask the Coordinator to identify environment requirements and resolve service or access questions. Save reusable setup in repository scripts and project settings. Validation retains the tested commit, settings and output for later inspection.

## Checks that need services

Use a repository-owned test wrapper that starts a disposable service, waits for readiness, runs the tests and stops its own resources before exiting. For example, a `test:isolated` script can choose an available loopback port and fresh test data, pass the endpoint to its tests, then clean up on success, failure or interruption. Keep the entire lifecycle within the command's timeout.

Each setup or validation command runs in a separate shell. Its exports do not carry forward, and Flowfield stops ordinary child processes when it finishes. Starting a background database in setup does not leave it available to the worker. Never detach or daemonize these processes. Services needed throughout a worker session require an explicitly agreed external arrangement; Flowfield does not provision them automatically.

For a shared service, agree its endpoint, data permissions, version and owner. Workers must leave borrowed services running. Cross-project references supply evidence, not running services.

## Let workers run saved checks

**Project settings → Integration → Allow saved checks outside the worker sandbox** lets workers call `run_project_checks` for the exact saved validation commands. It starts disabled. This permission runs the worker’s edited code with Flowfield’s service-host access, including access that the native harness may restrict. Enable it only for a project whose code and check scripts you trust. It does not approve code delivery or grant general native shell permission.

The worker cannot supply a command, working directory or environment to this operation. Commands run in its owned checkout with saved timeouts, bounded retained output and ordinary child-process cleanup. Latest full output is available through worker `read_context` pages and attempt evidence; final candidate validation still runs separately before approval.

Changing integration settings or replacing the registered repository directory invalidates permission. Enable the revised settings deliberately and start a fresh attempt to adopt changed commands. Revocation prevents future calls; stopping the worker cancels checks already running. Process cleanup uncertainty remains visible and reserves ownership until reconciled. Repository scripts must not detach services or modify shared data without explicit agreement.

## Choose workers

Workspace defaults apply across member projects. The **Task settings** icon opens **Worker** overrides; each attempt retains the harness, model and host registration it started with. Changes affect subsequent attempts, and unavailable choices fail explicitly rather than substituting a model.

The Coordinator's choice is independent. Supported Fast mode starts off. Enable it with the checkbox in workspace Worker or Reviewer settings, or override it for a task. Running attempts keep their saved choices. [Agent setup](/agents/overview) covers native accounts, discovery and permissions; [documents](/documents#supply-worker-context) covers the sources selected for workers.

Workers use separate Git worktrees and scoped Flowfield connections. Git isolation separates repository edits, not the whole host: use separate ports, databases and other mutable resources for concurrent tasks, or serialize them. Native access modes govern agent tools; configured setup and validation commands run directly on the service host.

## Try a result

Opening an exact code result prepares an independent copy of that candidate. Its **Run result** section shows a complete, copyable launcher. Run it in your terminal, or ask the Coordinator to run it, to execute setup followed by the saved Run command.

For an app with an API or database, use a repository-owned launcher that prepares all components, uses isolated ports and data, waits for readiness and prints the browser URL and stop instructions. Define representative sample data in workspace guidance and reuse the project’s seed scripts for populated previews. Workers verify that launch during implementation; checks of the exact service-generated Run result launcher happen after candidate preparation through focused review verification.

Existing copies keep their files and saved settings. A later delivery does not update them automatically. Open the result you intend to try, and follow any displayed preparation or destination recovery action.
