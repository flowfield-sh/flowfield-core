## People and agents

Requirements, design and implementation develop together. You and the **coordinator**
shape intent, priorities and review through your coding
conversation. **Workers** implement bounded assignments. The **service** schedules
ready work, preserves execution facts and delivers explicitly approved code.

The coordinator can continue planning while workers run. Closing its conversation
does not stop the service's enabled queue. The browser gives you direct control of
priorities, answers, pause, stop and approval.

Flowfield uses **ACP** to communicate with its built-in coding harnesses and **MCP** to
give agents project/task tools. See [ACP and MCP](/protocols) for the connections and
supported capabilities; [Integrations](/integrations/overview) covers setup.

## Projects, tasks and milestones

A **project** is an existing directory registered through the browser's directory chooser
or `flowfield project init`. The Coordinator belongs to a project. Its settings identify
the worker environment, model, checks and code delivery branch.

A **task** expresses an agreed outcome and success criteria. Its stable key, such as
`APP-1`, links to the same task across the browser, CLI and MCP. Tasks can depend on
other tasks in the same project; an incomplete prerequisite blocks execution.

A **milestone** groups related tasks. Dependencies connect tasks, not milestones.

## The task feed

Each task has a feed bringing together its definition and revisions, progress, worker attempts,
questions, answers, testing observations and results. Open a card to view its feed beside
the Coordinator. Discuss scope, queue changes and result questions with the coordinator.
Task inputs answer a specific question, request changes or confirm approval for an exact
result with an optional testing comment. Saved answers, feedback and approvals appear in
the feed; the task footer keeps the relevant controls and input errors.
Definition history highlights changed words and shows before/after values for fields.

Answering a worker question lets the service continue work when the queue permits it.
Project planning questions are handled by the coordinator when you resume its conversation.
Asking about a result does not automatically request changes. Earlier results and testing
observations remain inspectable.

**Current tokens**, below worker output, shows the agent's latest context-window report.
Hover or focus the ring for its reported token count and capacity. This measures the current
context rather than total tokens consumed across the task.

An ongoing worker attempt stays at the bottom of the feed as progress events arrive. After
completion, its output remains in that attempt event; the result contains the worker report
and review evidence. Press Escape in a task reply composer to cancel it without closing the task.

## The board and queue

Every task has one to eight outcome stages, including drafts. Your coordinator includes
the initial stages when creating a task and keeps them aligned when its definition changes.
Manual creation starts with one stage describing the entered outcome. Workers report
progress against those stages; completing them does not approve code or mark a task Done.

Tasks move through **Backlog**, **Up next**, **In progress**, **In review** and **Done**.
Each column scrolls independently below its heading. On narrow screens, scroll the board
horizontally to reach the other columns.

Up next expresses your execution priorities. Run queue enables eligible starts; an enabled
empty queue stays enabled. New ready tasks can start when added to it.

The queue starts paused, including after restart. Pause leaves active work running.
Each project starts with one worker slot; two independent tasks can run in separate
checkouts after you increase the maximum to two. Waiting for review frees the worker slot.
The queue shows active workers against that maximum, such as **1/2 active**.
**Retry worker** queues a fresh attempt with the preserved work; it respects queue pause,
dependencies and available slots.

**Needs you** collects questions, reviews and interventions. The browser's Connected
indicator describes its live update stream.

## Agent settings and permissions

Project worker defaults and task overrides use the same harness/model choice, with
reasoning effort and access mode only where the harness supports those controls.
Each attempt saves the choice it used. Changing defaults does not alter running attempts
or explicit task overrides. Unavailable choices fail explicitly instead of selecting
another model.

Fast mode is available only for models that support it. Workers start with Fast off; enable it
per task using the lightning button. There is no project-wide speed default. The Coordinator
has its own Fast choice. Changes affect subsequent attempts and can increase usage;
historical attempts keep their original choices.

Each project has one [Coordinator](/coordinator), with its model, effort and access mode
selected beside the chat input. Changes apply to subsequent messages and do not configure
your standalone coding agent.

Agents use the tools and credentials on the machine running Flowfield. Codex supplies
the available access modes; choose one beside the Coordinator input or in Workers settings.

Tool permission requests from connected harness sessions have durable answers
and response controls in the Coordinator, the task view and **Needs you**. Requests expire or close when
their live turn ends; saved answers are never replayed into another session. A tool
permission decision does not approve a result or authorize code delivery.

## Notifications

Notifications collect task-attention alerts, operation errors and available updates.
Flowfield saves them in the workspace, so notices and dismissals are shared across browsers
and survive restarts. Dismissing a notice does not answer a question, approve code or change
the queue. Clear notifications dismisses the currently observed set; newer notices stay visible.
Flowfield keeps the 200 most recent notification records.

Desktop alerts are optional: choose **Enable browser notifications** and allow them in your
browser. Permission is required in each browser. Desktop delivery is best effort, with one
attempt shared across tabs and browsers; the saved notification list remains available.
An open browser is required for desktop alerts. See [installation](/installation#update)
for automatic and manual update checks.

## Results and approval

A result contains the worker's outcome and verification evidence. Code approval names
an exact candidate and destination. Approval in your coding conversation uses the same
record as browser approval, without a second confirmation there.

The service validates and delivers approved code. Done means the agreed outcome has
completed, including code delivery. A checkout blocker preserves approval for a delivery
retry; a changed candidate needs its own review. Inspection is optional and never grants
approval by itself.

## Working with an existing project

Keep architecture, designs, coding conventions and testing philosophy in the repository’s
existing documents and agent instructions. Flowfield tracks ongoing assignments and their
execution evidence. Reference
authoritative files in task definitions instead of copying rules into every task.

During adoption, identify the delivery branch, reproducible setup commands and meaningful
checks for your project. Preserve its existing workflow. For parallel work, give tests and
services separate databases, ports and other mutable resources, or serialize that work.
