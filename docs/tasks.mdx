title: Tasks and execution
description: Turn an agreed outcome into focused work, with dependencies and optional local subtasks.

A task keeps an outcome, success criteria, context, activity and results together. Capture work in **Backlog** and move it to **Up next** when you want it executed. Code tasks belong to a project; reports and files can belong to the workspace.

Open a task for its definition, subtasks and activity. Use **Task settings** for agent overrides, Inbox for questions and results for approval.

## Define useful work

Describe the outcome and how you will judge it. The Coordinator can clarify the scope and select the documents the Worker needs. [Planning effective tasks](/planning-tasks) gives examples of requests and success criteria.

Tasks use workspace-local keys such as `T-1`. See [Files](/files) for working with reports, datasets and images.

Each execution captures the task and its selected guidance. See [Keep tasks current](/documents#keep-tasks-current) for how guidance changes reach unfinished work.

Done is permanent. For follow-up work, ask the Coordinator to create a new task referencing the completed result.

## Priorities and queue

| Column | Meaning |
| --- | --- |
| Backlog | Work you have captured but are not prioritizing for execution. |
| Up next | Your ordered execution priorities, including tasks with unmet conditions. |
| In progress | Work, checks or independent review are running, queued or awaiting recovery. |
| In review | A result needs a human decision or approved delivery is pending. |
| Done | The agreed outcome is complete, including required code delivery. |

Drag cards within Backlog and Up next to prioritize work. The queue follows that order, skipping tasks whose setup, inputs or dependencies are not ready. Card status shows what is needed.

New workspaces start paused with five worker slots. **Run queue** starts eligible work; **Pause queue** leaves active work running. Set capacity and **Auto-start worker queue** in **Workspace settings → Workers**.

Agent-setting changes apply to the next attempt. Missing or unavailable choices block work until corrected.

Each board column scrolls independently. On narrow screens, scroll sideways to reach the other columns.

## Edit a task

Move queued work back to Backlog before editing; stop active work first. In **Backlog**, choose **Edit task** to change the title, description, acceptance criteria or labels, then **Save task**. Project assignment stays fixed. If the task leaves Backlog while you edit, Save becomes unavailable. **Cancel** lets you discard unsaved changes and return to the task.

## Archive or delete

**Archive task** hides work while keeping its history. Stop active work first and resolve shared questions. Restore returns the task to its previous column.

**Delete task** permanently removes its history, results, files and working copies. Stop previews and save useful edits before confirming. Delivered code stays in your repository. Active work or references from other tasks block deletion; archive instead. The Coordinator can also delete tasks.

## Dependencies

Tasks can depend on other tasks in the same workspace, including other projects. Dependents wait for delivered results; archiving unfinished work does not satisfy them. Cross-project dependencies do not share checkouts or merge code into the dependent repository.

If a task needs files from a prerequisite, ask the Coordinator to select those retained files as inputs. Keep it in Backlog until the files exist and the handoff is complete, then move it to Up next.

Completed tasks keep their delivered results when dependencies change.

## Work within a task

![A task with local subtasks, dependencies and its activity feed](/images/task.png)

Ask the Coordinator to split work into subtasks when contributions can run independently or have useful dependencies. Subtasks appear inside their parent task.

Subtask dependencies stay within the parent. Independent contributions can run in parallel; dependent ones receive their prerequisites’ code and files. Dependencies on other tasks belong on the parent.

Flowfield combines the contributions into one result for review and code approval. File and report tasks use the same review flow.

Corrections can rerun affected subtasks and dependents while keeping independent work. Earlier results remain in history.

Tool permission requests need an answer while the session is waiting. Stopping it cancels pending requests.

## Follow an attempt

Open an **In progress** task to follow activity. Workers finish by submitting a result or asking a blocking question.

If a worker finishes without either, Flowfield reminds it once. If it still does not report, inspect the preserved work and retry explicitly.

Choose **Stop task** and confirm to stop active Worker or Reviewer execution and return the task to Backlog. Work and history remain. **Retry worker** queues a fresh attempt; follow the displayed recovery action if cleanup is uncertain.

## Read the task story

The feed groups changes, questions, activity and results into initial work, corrections and follow-ups. Expand an event for details; contribution events name their subtask. Older streamed activity may expire, while task events, results and files remain.

Activity follows new output until you scroll up. Task **Metrics** shows lifetime Tokens, Cost, Duration and Corrections; open a callout for details. See [Metrics](/metrics#explore-workspace-activity) to compare activity across tasks.

Use **View result** to open the latest result, or find earlier results in the feed. Request and result links open their response and recovery controls.
