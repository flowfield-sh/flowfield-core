A task owns an outcome, its success criteria, sources, activity, results and final delivery. Ask the Coordinator to create and prepare tasks; use **Task Board** to follow the plan. Repository work belongs to one project. Reports and files can belong directly to the workspace.

Open a task to read its purpose, related work, optional **Subtasks** and chronological feed. The **Task settings** icon beside the title opens Worker and Reviewer overrides; **View task** returns to the task. Questions and result decisions open in [Inbox or their exact request](/inbox); [results](/review) own inspection, feedback and approval.

## Define useful work

Describe the outcome and how you will judge it. The Coordinator can clarify the scope, select [worker documents](/documents#supply-worker-context) and prepare the assignment. The Coordinator maintains task definitions and labels; priorities are also available directly on the board.

For reports, datasets, images and other files, ask for a workspace task. All tasks use workspace-local keys such as `T-1` and `T-2`, whether or not they have a project. It uses the same queue, questions and result history as project work. No project or Git setup is needed. [Files](/files) explains durable delivery, selected inputs and retained results.

The prepared description is the worker's resolved handoff: what to achieve and why, consequential constraints and exceptions, how completion can be observed, and which sources apply. The Coordinator resolves conflicting requirements before preparation and keeps scheduling discussion outside the assignment. Workers receive guidance for their current attempt, including saved answers or revision feedback when relevant.

Preparation fixes the task agreement and selected document revisions. Placing a task in Up next expresses priority, not readiness. Changes to an unstarted task's requirements or references require preparation again; after work starts, ask the Coordinator to reconcile changes with the existing work. Task notes retain discussion and evidence; they do not silently rewrite the assignment.

If completed work needs correction, ask the Coordinator to reopen the same task. It returns to Backlog as a draft, preserving its earlier results, approvals and history. The Coordinator prepares fresh requirements before scheduling the follow-up. New code requires its own approval; the earlier delivery stays recorded.

## Priorities and queue

| Column | Meaning |
| --- | --- |
| Backlog | Work you have captured but are not prioritizing for execution. |
| Up next | Your ordered execution priorities, including tasks with unmet conditions. |
| In progress | Work that has started, with activity or recovery actions in its feed. |
| In review | A result needs a decision. |
| Done | The agreed outcome is complete, including required code delivery. |

Drag a card’s move handle to order Backlog and Up next or move work between them. You can also ask the Coordinator. The shared scheduler follows Up next order and skips work whose project, input or prerequisites are not ready. Read the card's status for the specific next action.

New workspaces start paused with capacity for five parallel workers. **Run queue** enables eligible starts; **Pause queue** prevents new starts while active workers continue. **Workspace settings → Workers → Auto-start worker queue** controls whether the queue runs when Flowfield starts. Save changes to apply this preference. Sidebar Run/Pause changes only the current queue. Missing role settings or unavailable harness/model choices block a task before a worker starts. Update the relevant settings, then eligible work resumes through the queue. Workspace changes apply to inheriting tasks on their next attempt; running attempts keep their captured settings. Adjust **Maximum parallel workers** in **Workspace settings → Workers** to suit your projects. Waiting for review frees a worker slot.

Each board column scrolls independently. On narrow screens, scroll sideways to reach the other columns.

## Dependencies

A task can depend on tasks in other projects within the same workspace. Prerequisites must finish before dependent work starts; cycles and cross-workspace dependencies are rejected. A dependency is satisfied by the task’s delivered result. A review recommendation or completed subtask alone does not release dependent tasks. Foreign prerequisite code is not merged into that repository's Git history.

Completed tasks retain their delivered results and captured inputs when prerequisite work changes later. They do not need updating or reconciling. Create a new task for a new outcome, or explicitly reopen the task you want to correct; earlier results remain available. Unfinished dependent work still requires ready prerequisites and reconciliation when its inputs change. Archiving unfinished work does not satisfy its dependents.

## Work within a task

![A task with local subtasks, dependencies and its activity feed](/images/task.png)

A task can run directly or contain one level of subtasks. Ask the Coordinator to split work when independent contributions or a concrete dependency make execution clearer. Subtasks appear directly in the task’s **Subtasks** section; the board and sidebar continue to show the task.

Subtask dependencies belong only to that parent task. Independent contributions may run in parallel within workspace capacity. A dependent contribution receives its prerequisites’ code and retained files. Each contribution gets its own managed worker session. Native subagents, when supported and enabled by the harness, remain inside that session; Flowfield does not schedule them as separate tasks or count them as separate worker slots. External dependencies belong on the parent task.

When every contribution is ready, Flowfield assembles one task result and checks the combined code. The task reviewer assesses that whole outcome. There is one final code approval for delivery to the project’s configured destination. Reports, screenshots and PDFs follow the same task review flow without requiring Git.

A correction can target a contribution and invalidate its downstream dependents while retaining independent completed work. A changed task agreement or selected source requires fresh preparation. Earlier results, files and sign-offs remain in history.

Tool permission requests remain pending while the native session is waiting. Stopping the session or service cancels an undelivered request; saved decisions are never replayed into a replacement session. Task access settings apply to the next attempt.

## Follow an attempt

Open an **In progress** task to follow the worker's activity. The worker should finish by submitting an outcome with its checks and limitations, or asking a blocking question. A final chat summary alone does not create a reviewable result.

If a worker ends normally without a submission or question, Flowfield gives it one reminder in the same session and checkout. This uses another model turn and retains the slot until cleanup completes. If it still does not report, work is preserved for inspection and explicit retry. Stopped or interrupted attempts are never restarted by this reminder.

Ask the Coordinator to stop active task workers; unfinished work is preserved. **Retry worker** queues a fresh attempt; it respects pause, dependencies and capacity. Follow the displayed recovery action if native cleanup is uncertain.

## Read the task story

The feed keeps definition changes, captured sources, questions, answers, worker activity, numbered results and reviewer sign-offs in order. Work cycles group initial work, corrections and follow-ups after reopening. Events start collapsed; expand the evidence you need. Exact-time tooltips accompany relative timestamps.

The task page stays at your reading position. Open worker or reviewer output to follow new entries inside that panel; scroll up to read earlier output and return to the bottom to follow again. Manual disclosure choices survive work-tab navigation. Numeric context occupancy and reported consumed tokens are separate measurements.

The task is a record of the work. Follow its request or result link to answer, request changes, retry a failed review or approve code. Use the Archive icon beside the task title to set work aside. Stop active execution and checks, or wait for integration first. Task-only questions and pending replies are withdrawn or cancelled; shared questions must be resolved first. Restoring retains the task’s earlier state and history. Archive is not completion.
