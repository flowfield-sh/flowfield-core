description: Prioritize work, resolve questions and decide which exact results to deliver.

A task keeps its definition, revisions, stages, worker activity, questions and results together. Open it from Work or the Board to see its intended outcome, current state, blockers, available result and captured document references beside the Coordinator. Expand **Work details** for stages. The task header shows a status dot, task key and title; hover or focus the dot for its meaning. Labels and view tabs sit below the header. The **Activity** tab keeps the full conversation in compact rows; click an event or activate it with the keyboard to expand its report or evidence. Exact event links open the selected entry, and active worker output stays expanded. Discuss the plan in the Coordinator conversation; task inputs answer a particular question, request changes or approve a selected result.

## Define useful work

Describe the outcome and how you will judge it. The Coordinator can clarify the scope, select [worker documents](/documents#supply-worker-context), define one to eight outcome stages and prepare the assignment. Tasks, milestones, labels and priorities are maintained through that conversation.

The prepared description is the worker's resolved handoff: what to achieve and why, consequential constraints and exceptions, how completion can be observed, and which sources apply. The Coordinator resolves conflicting requirements before preparation and keeps scheduling discussion outside the assignment. Workers receive guidance for their current attempt, including saved answers or revision feedback when relevant.

Preparation fixes the task agreement and selected document revisions. Placing a task in Up next expresses priority, not readiness. Changes to an unstarted task's requirements or references require preparation again; after work starts, ask the Coordinator to reconcile changes with the existing work. Task notes retain discussion and evidence; they do not silently rewrite the assignment.

If completed work needs correction, ask the Coordinator to reopen the same task. It returns to Backlog as a draft, preserving its earlier results, approvals and history. The Coordinator prepares fresh stages and requirements before scheduling the follow-up. New code requires its own approval; the earlier delivery stays recorded.

## Priorities and queue

| Column | Meaning |
| --- | --- |
| Backlog | Work you have captured but are not prioritizing for execution. |
| Up next | Your ordered execution priorities, including tasks with unmet conditions. |
| In progress | Work that has started, with activity or recovery actions in its feed. |
| In review | A result needs a decision. |
| Done | The agreed outcome is complete, including required code delivery. |

Ask the Coordinator to order Backlog and Up next or move work between them. The shared scheduler follows Up next order and skips work whose project, input or prerequisites are not ready. Read the card's status for the specific next action.

New workspaces start paused with one worker slot. **Run queue** enables eligible starts; **Pause queue** prevents new starts while active workers continue. The saved queue choice survives service restarts. Increase **Maximum parallel workers** in **Workspace settings → Workers** when independent tasks can safely run together. Waiting for review frees a worker slot.

Each board column scrolls independently. On narrow screens, scroll sideways to reach the other columns.

## Dependencies

A task can depend on tasks in other projects within the same workspace. Prerequisites must finish before dependent work starts; cycles and cross-workspace dependencies are rejected. Each dependent task retains its own checkout and delivery branch. Foreign prerequisite code is not merged into that repository's Git history.

Reopening or changing completed prerequisite work can require downstream reconciliation. Archiving unfinished work does not satisfy its dependents. Ask the Coordinator to review affected tasks when the plan changes.

## Follow an attempt

Open an **In progress** task to follow the worker's activity and reported stages. The worker should finish by submitting an outcome with its checks and limitations, or asking a blocking question. A final chat summary alone does not create a reviewable result.

If a worker ends normally without either, Flowfield immediately gives it one reminder in the same session and checkout. The reminder appears in activity and asks it to report the work already performed, including partial progress or a blocking question when appropriate. The worker keeps its existing tools and permissions; submitted code still requires your exact approval.

Normal submissions need no extra model turn. When the reminder is needed, it uses additional model tokens; its cost depends on the session context, model and caching, not just the reminder's length. It keeps the worker slot occupied until the attempt ends and cleanup is confirmed. If the worker still finishes without a submission or question, work is preserved and the attempt needs inspection and explicit retry.

**Stop worker** ends an active attempt, including one responding to a reminder, and preserves its unfinished work. **Retry worker** queues a fresh attempt; it respects pause, dependencies and capacity. Follow the displayed recovery action if native cleanup is uncertain. The reporting reminder does not restart stopped or interrupted attempts.

## Work through Inbox

Inbox gathers human decisions across the workspace in **Needs me** and keeps past responses in **History**, including answers awaiting Coordinator follow-up. Its badge counts actionable requests; the project filter narrows the view. Each request identifies its source, explains the decision and offers the relevant response controls directly in Inbox. Expand evidence or follow the source link when you need more context.

Resolved requests disappear from **Needs me** as you respond. Drafts on other requests stay in place, including on pages you have already loaded. Failed saves keep your input; if another session resolves a request while you are writing, discard your retained draft when you are ready.

| Item | Next action |
| --- | --- |
| Question | Read the context, choose a suggested answer or write your own, then send it. Worker answers continue managed work when eligible; planning answers need the Coordinator to resume and reconcile them. |
| Code review | Read the selected result and destination, optionally try or inspect it, then request changes or approve and integrate it. |
| Milestone acceptance | Review the checks and their evidence, then accept the milestone or request changes with feedback. |
| Intervention | Inspect the failure or blocker and follow its recovery action. |
| Tool permission | Allow or deny the native request while its turn is waiting. This grants no code-delivery approval. |

Suggested answers fill the composer; selecting one does not send it. Responses stay bound to the question or result you were reviewing. If that request changes while you are typing, your draft is preserved and cannot silently approve or answer its replacement.

Saved worker answers need no separate human apply step. Once assigned to a continuation, the answer remains in history; send a correction as new input rather than replacing it. Answering or retrying never enables a paused queue. The same actions are available from the task, and the Coordinator can help sort the Inbox and follow up. **Needs me** contains only unresolved requests. Once resolved, an item moves to compact **History**; if you still have an unsent response, it remains bound to that record in History until you discard it. Approved results with blocked delivery remain actionable as recovery requests.

## Review an exact result

Read the worker report, limitations and checks against the task's success criteria. Project checks and worker-authored tests are useful evidence; try representative inputs or ask the Coordinator to investigate gaps before deciding what ships.

**Code changes** shows the candidate's changed files and diff. **Try result** prepares an independent copy and a launcher using the project's saved run configuration. See [worker setup](/worker-setup#try-a-result). Trying or inspecting a result grants no approval.

![Code changes and exact-result review beside the Coordinator](/images/code-review.png)

Choose **Request changes** to send concrete feedback for another pass. Attach relevant files or testing observations when needed. Or choose **Approve and integrate**, confirm the selected result and optionally include a testing comment. Explicit approval in the Coordinator conversation records the same exact decision without a second browser confirmation.

Flowfield checks and delivers the approved candidate to the configured project checkout. Conflicting local changes remain intact. Resolve the reported blocker and use its delivery retry action; if the candidate changes, review and approve the new result. A complete report-only result can finish without code approval.

## Stay oriented

Saved definitions, answers, feedback and results remain in the task feed. Older results stay inspectable; links to exact results preserve their identity. **Current tokens** reports the harness's latest context occupancy, not total task usage.

Optional Inbox notifications link back to the item. Configure in-app and system delivery in **Settings → Notifications**; system notifications require browser permission and an open Flowfield page. Closing an alert answers no question and approves no result. Update announcements lead to **Settings → Updates**; see [installation](/installation#update).

Ask the Coordinator to archive work you set aside after reconciling active work, reviews and questions. Restoring a task retains its previous work state; Archive is not completion.

## Assemble and review a milestone

Ask the Coordinator to configure milestone delivery before preparing its tasks. Flowfield owns a separate branch and checkout for the milestone, while the project's destination remains the final delivery target. This delivery mode supports one repository per milestone. Existing milestones remain ordinary task groups until delivery is configured; prepared tasks are not moved automatically.

Approve each contribution as usual. Its result names the milestone branch as its destination. Dependent tasks see delivered contributions on that branch; the original project checkout stays unchanged. A dependency from another branch cannot start until its required code is available in the receiving task's baseline.

Once contributions are complete, the Coordinator prepares whole-milestone verification. Flowfield combines the milestone work with the current project destination, runs configured checks, and starts the verifier from that exact candidate. The report lists the agreed checks and evidence. **Try milestone** prepares an independent copy of the same candidate; **Code changes** shows the combined changes. Opening inspection starts no application process. Follow its terminal command to run the project and stop it with Ctrl+C when finished.

Choose **Accept and promote** to authorize that verified candidate for the named local destination. The request leaves Inbox immediately; the milestone remains in Review until delivery succeeds. Flowfield does not push or deploy. If local edits block delivery, resolve your files and choose **Retry promotion**; the exact approval is retained. Changes to the milestone, contributions, source, destination or settings require a new verification and review. Inspection copies and earlier evidence are preserved.

Milestones without owned delivery retain **Accept milestone**, which records review of their delivered outcomes without another code integration.
