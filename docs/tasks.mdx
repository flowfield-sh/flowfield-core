Open a task from Work or Tasks. **Task** shows its purpose, related work and chronological conversation. Local subtasks appear directly beneath its purpose. **View result** opens the exact Result Request with checks, inspection and review controls. **Settings** configures its worker and reviewer overrides.

The task feed keeps dated definition changes, captured sources, questions, worker attempts and results. Expand a row to read its evidence; timestamp links select an exact event, and only the latest active event opens automatically. Discuss plans in the Coordinator. Task inputs answer a particular question, request changes or approve a selected result.

Each Inbox ask has a stable **Request** link. Use the header’s **Open request in work tab** button to respond in a separate tab; the source badge opens its task or project. Inbox History opens the same Request after resolution. Drafts and responses are shared across these views, and earlier requests keep their original evidence and approval bindings. The Coordinator can reference requests directly with `list_requests` and `get_request`.

## Define useful work

Describe the outcome and how you will judge it. The Coordinator can clarify the scope, select [worker documents](/documents#supply-worker-context) and prepare the assignment. Tasks, labels and priorities are maintained through that conversation.

For reports, datasets, images and other files, ask for a workspace task. All tasks use workspace-local keys such as `T-1` and `T-2`, whether or not they have a project. It uses the same queue, questions and result history as project work. No project or Git setup is needed. [Files](/files) explains durable delivery, selected inputs and retained results.

The prepared description is the worker's resolved handoff: what to achieve and why, consequential constraints and exceptions, how completion can be observed, and which sources apply. The Coordinator resolves conflicting requirements before preparation and keeps scheduling discussion outside the assignment. Workers receive guidance for their current attempt, including saved answers or revision feedback when relevant.

Preparation fixes the task agreement and selected document revisions. Placing a task in Up next expresses priority, not readiness. Changes to an unstarted task's requirements or references require preparation again; after work starts, ask the Coordinator to reconcile changes with the existing work. Task notes retain discussion and evidence; they do not silently rewrite the assignment.

If completed work needs correction, ask the Coordinator to reopen the same task. It returns to Backlog as a draft, preserving its earlier results, approvals and history. The Coordinator prepares fresh requirements before scheduling the follow-up. New code requires its own approval; the earlier delivery stays recorded.

## Priorities and queue

| Column | Meaning |
| --- | --- |
| Backlog | Work you have captured but are not prioritizing for execution. |
| Up next | Your ordered execution priorities, including tasks with unmet conditions. |
| In progress | Work that has started, with activity or recovery actions in its feed. |
| In review | A result needs a decision. |
| Done | The agreed outcome is complete, including required code delivery. |

Ask the Coordinator to order Backlog and Up next or move work between them. The shared scheduler follows Up next order and skips work whose project, input or prerequisites are not ready. Read the card's status for the specific next action.

New workspaces start paused with one worker slot. **Run queue** enables eligible starts; **Pause queue** prevents new starts while active workers continue. The saved queue choice survives service restarts. Missing role settings or unavailable harness/model choices block a task before a worker starts. Update the relevant settings, then eligible work resumes through the queue. Workspace changes apply to inheriting tasks on their next attempt; running attempts keep their captured settings. Increase **Maximum parallel workers** in **Workspace settings → Workers** when independent tasks can safely run together. Waiting for review frees a worker slot.

Each board column scrolls independently. On narrow screens, scroll sideways to reach the other columns.

## Dependencies

A task can depend on tasks in other projects within the same workspace. Prerequisites must finish before dependent work starts; cycles and cross-workspace dependencies are rejected. A dependency is satisfied by the task’s delivered result. A review recommendation or completed subtask alone does not release dependent tasks. Foreign prerequisite code is not merged into that repository's Git history.

Reopening or changing completed prerequisite work can require downstream reconciliation. Archiving unfinished work does not satisfy its dependents. Ask the Coordinator to review affected tasks when the plan changes.

## Follow an attempt

Open an **In progress** task to follow the worker's activity. The worker should finish by submitting an outcome with its checks and limitations, or asking a blocking question. A final chat summary alone does not create a reviewable result.

If a worker ends normally without either, Flowfield immediately gives it one reminder in the same session and checkout. The reminder appears in activity and asks it to report the work already performed, including partial progress or a blocking question when appropriate. The worker keeps its existing tools and permissions; submitted code still requires your exact approval.

Normal submissions need no extra model turn. When the reminder is needed, it uses additional model tokens; its cost depends on the session context, model and caching, not just the reminder's length. It keeps the worker slot occupied until the attempt ends and cleanup is confirmed. If the worker still finishes without a submission or question, work is preserved and the attempt needs inspection and explicit retry.

**Stop task** stops its active workers, preserves their work and returns the task to Backlog. **Retry worker** queues a fresh attempt; it respects pause, dependencies and capacity. Follow the displayed recovery action if native cleanup is uncertain. The reporting reminder does not restart stopped or interrupted attempts.

## Work through Inbox

Inbox gathers human decisions across the workspace in **Needs me** and keeps past responses in **History**, including answers awaiting Coordinator follow-up. Its badge counts actionable requests. Each request identifies its source, explains the decision and offers the relevant response controls directly in Inbox. Expand evidence or follow the source link when you need more context. Resource links from Inbox open a separate work tab; Inbox keeps its selected view.

Resolved requests disappear from **Needs me** as you respond. Drafts on other requests stay in place, including on pages you have already loaded. Failed saves keep your input; if another session resolves a request while you are writing, discard your retained draft when you are ready.

| Item | Next action |
| --- | --- |
| Question | Read the context, choose a suggested answer or write your own, then send it. Worker answers continue managed work when eligible; planning answers need the Coordinator to resume and reconcile them. |
| Result | Read the selected result and destination, optionally try or inspect it, then request changes or approve and integrate it. |
| Intervention | Inspect the failure or blocker and follow its recovery action. |
| Tool permission | Allow or deny the native request while its turn is waiting. This grants no code-delivery approval. |

Suggested answers fill the composer; selecting one does not send it. Responses stay bound to the question or result you were reviewing. If that request changes while you are typing, your draft is preserved and cannot silently approve or answer its replacement.

Saved worker answers need no separate human apply step. Once assigned to a continuation, the answer remains in history; send a correction as new input rather than replacing it. Answering or retrying never enables a paused queue. The same actions are available from the task, and the Coordinator can help sort the Inbox and follow up. **Needs me** contains only unresolved requests. Once resolved, an item moves to compact **History**; if you still have an unsent response, it remains bound to that record in History until you discard it. Approved results with blocked delivery remain actionable as recovery requests.

## Independent task review

In **Workspace settings → Reviewers**, choose the native harness and model for **Task reviewer**. Assessment defaults on, but no model is selected automatically. A task's **Settings** can override the workspace choice or reset to inheritance. Subtasks use their parent task’s worker settings and have no separate reviewer.

Complete code and file outcomes receive an independent assessment against their exact assignment, sources, destination and saved validation. Reviews share worker capacity and respect the queue: pausing prevents new rounds, while an active round continues. The reviewer inspects the saved candidate and validation evidence; this review does not execute project checks itself.

Reviewer sign-offs appear on the task and in the exact result. The reviewer can ask the implementer a scoped clarification, request an in-scope correction, or send an intent, scope or access question to Inbox. Saved human answers continue the review without another apply step. A correction produces a new candidate and fresh independent assessment. Changes to the agreement or authority require Coordinator reconciliation; an answer does not silently amend them. Waiting for an answer releases capacity.

**Stop review** preserves the candidate and findings. Failed or stopped reviews require explicit **Retry review**. If cleanup is uncertain, inspect **Review rounds and diagnostics**, confirm the retained processes have stopped, then retry. Uncertain execution keeps its capacity reserved. Changed inputs make an assessment outdated and retain its evidence; questions belonging to that assessment are withdrawn with their saved answers preserved.

An independent approval recommends the candidate. Code delivery still needs your exact approval. Complete file and report results finish after the configured review. Stop an active review before making a manual result decision. Assessment alone grants no delivery authority.

## Review an exact result

Read the worker report, limitations and checks against the task's success criteria. Project checks and worker-authored tests are useful evidence; try representative inputs or ask the Coordinator to investigate gaps before deciding what ships.

**Code changes** shows the candidate's changed files and diff. **Try result** prepares an independent copy and a launcher using the project's saved run configuration. See [worker setup](/worker-setup#try-a-result). Trying or inspecting a result grants no approval.

![Code changes and exact-result review beside the Coordinator](/images/code-review.png)

Choose **Request changes** to send concrete feedback for another pass. Attach relevant files or testing observations when needed. Or choose **Approve and integrate**, confirm the selected result and optionally include a testing comment. Explicit approval in the Coordinator conversation records the same exact decision without a second browser confirmation.

Flowfield checks and delivers the approved candidate to the configured project checkout. Conflicting local changes remain intact. Resolve the reported blocker and use its delivery retry action; if the candidate changes, review and approve the new result. A complete report-only result can finish without code approval.

## Stay oriented

Saved definitions, answers, feedback and results remain in the task feed. Older results stay inspectable; links to exact results preserve their identity. **Current tokens** reports the harness's latest context occupancy, not total task usage.

Optional Inbox notifications link back to the item. Configure in-app and system delivery in **Settings → Notifications**; system notifications require browser permission and an open Flowfield page. Closing an alert answers no question and approves no result. Update announcements lead to **Settings → Updates**; see [installation](/installation#update).

Ask the Coordinator to archive work you set aside after reconciling active work, reviews and questions. Restoring a task retains its previous work state; Archive is not completion.

## Work within a task

A task can run directly or contain one level of subtasks. Ask the Coordinator to split work when independent contributions or a concrete dependency make execution clearer. Subtasks appear under the task’s **Work** disclosure; the board and sidebar continue to show the task.

Subtask dependencies belong only to that parent task. Independent contributions may run in parallel within workspace capacity. A dependent contribution receives its prerequisites’ code and retained files. External dependencies belong on the parent task.

When every contribution is ready, Flowfield assembles one task result and checks the combined code. The task reviewer assesses that whole outcome. There is one final code approval for delivery to the project’s configured destination. Reports, screenshots and PDFs follow the same task review flow without requiring Git.

A correction can target a contribution and invalidate its downstream dependents while retaining independent completed work. A changed task agreement or selected source requires fresh preparation. Earlier results, files and sign-offs remain in history.

Tool permission requests remain pending while the native session is waiting. Stopping the session or service cancels an undelivered request; saved decisions are never replayed into a replacement session. Task access settings apply to the next attempt.
