title: Tasks and execution

A task owns an outcome, its success criteria, sources, activity, results and final delivery. Ask the Coordinator to create and prepare tasks; use **Task Board** to follow the plan. Repository work belongs to one project. Reports and files can belong directly to the workspace.

Completed tasks show **Done**. **Delivered** identifies their recorded results in Inbox and delivery history.

Open a task to read its definition, related work, subtasks and feed. **Task settings** in the header opens Worker and Reviewer overrides. Answer questions in [Inbox](/inbox) and inspect or approve [results](/review) from their own views.

## Define useful work

Describe the outcome and how you will judge it. The Coordinator can clarify the scope, select [worker documents](/documents#supply-worker-context) and prepare the assignment. You and the Coordinator can edit task definitions and labels; priorities are also available directly on the board.

Tasks use workspace-local keys such as `T-1`. For reports, datasets or images, ask for a workspace task without a project. See [Files](/files) for outputs and inputs.

A prepared assignment gives the worker the outcome, constraints, success criteria and selected sources. Resolve conflicting requirements with the Coordinator before preparation; saved answers and correction feedback accompany subsequent attempts.

Preparation records the agreement and latest selected guidance. Placing a task in Up next expresses priority, not readiness. Flowfield [reconciles guidance changes automatically](/documents#keep-tasks-current) at work and review handoffs. Discuss changes to the intended outcome with the Coordinator. Task notes retain discussion and evidence; they do not rewrite the assignment.

If completed work needs correction, ask the Coordinator to reopen the same task. It returns to Backlog as a draft, preserving its earlier results, approvals and history. The Coordinator prepares fresh requirements before scheduling the follow-up. New code requires its own approval; the earlier delivery stays recorded.

## Priorities and queue

| Column | Meaning |
| --- | --- |
| Backlog | Work you have captured but are not prioritizing for execution. |
| Up next | Your ordered execution priorities, including tasks with unmet conditions. |
| In progress | Work, checks or independent review are running, queued or awaiting recovery. |
| In review | A result needs a human decision or approved delivery is pending. |
| Done | The agreed outcome is complete, including required code delivery. |

Drag a card’s move handle to order Backlog and Up next or move work between them. You can also ask the Coordinator. The shared scheduler follows Up next order and skips work whose project, input or prerequisites are not ready. Read the card's status for the specific next action.

New workspaces start paused with capacity for five parallel workers. **Run queue** enables eligible starts; **Pause queue** prevents new starts while active workers continue. In **Workspace settings → Workers**, save the model, **Maximum parallel workers** and **Auto-start worker queue** together. Auto-start controls whether the queue runs when Flowfield starts; sidebar Run/Pause changes only the current queue.

Missing role settings or unavailable harness/model choices block a task before a worker starts. Update the relevant settings, then eligible work resumes through the queue. Workspace changes apply to inheriting tasks on their next attempt; running attempts keep their captured settings. Waiting for review frees a worker slot.

Each board column scrolls independently. On narrow screens, scroll sideways to reach the other columns.

## Edit a task

Choose **Edit task** in the task header to change its title, description, acceptance criteria or labels, then **Save task**. Project assignment stays fixed. Changes appear as task-definition updates in the feed. Unsaved edits stay protected when navigating; if someone changes the task before you save, use **Load latest** to review the current definition. Changes to requirements can require reconciliation of recorded work with the Coordinator.

## Archive or delete

Use **Archive task** in the task header to hide abandoned work while retaining its history and inspection copies. Restore returns it to its previous column. Stop active work before archiving. Archiving withdraws task-only questions and cancels pending replies; resolve shared questions first.

**Delete task**, beside Archive, permanently removes the task, its history, results, submitted files and owned work folders, including inspection edits and preview data. Confirm the deletion after stopping any manually launched previews and saving anything you want to keep. Delivered code in your project stays. Active or uncertain managed work, dependent tasks and frozen file/evidence consumers block deletion. Archive instead when those references should remain. The Coordinator can also delete tasks through `delete_task`, using the same ownership and evidence checks.

Deletion removes the task from collections and closes its open tabs after refresh. Task numbers are never reused. See the [CLI](/cli#tasks-and-subtasks) for command-line deletion.

## Dependencies

Tasks can depend on other tasks in the same workspace, including other projects. Dependents wait for delivered results; archiving unfinished work does not satisfy them. Cross-project prerequisites supply context and files without merging their code into the dependent repository.

Completed tasks keep their delivered results and captured inputs when prerequisites change. Reopen the task for a correction or create a new task for new work. Unfinished tasks reconcile changed inputs before continuing; see [result follow-ups](/review#earlier-results-and-follow-ups).

## Work within a task

![A task with local subtasks, dependencies and its activity feed](/images/task.png)

A task can run directly or contain one level of subtasks. Ask the Coordinator to split work when independent contributions or a concrete dependency make execution clearer. Subtasks appear directly in the task’s **Subtasks** section; the board and sidebar continue to show the task.

Subtask dependencies belong only to that parent task. Independent contributions may run in parallel within workspace capacity. A dependent contribution receives its prerequisites’ code and retained files. Each contribution gets its own managed worker session. Native subagents, when supported and enabled by the harness, remain inside that session; Flowfield does not schedule them as separate tasks or count them as separate worker slots. External dependencies belong on the parent task.

When every contribution is ready, Flowfield assembles one task result and checks the combined code. The task reviewer assesses that whole outcome. There is one final code approval for delivery to the project’s configured destination. Reports, screenshots and PDFs follow the same task review flow without requiring Git.

A correction can target a contribution and invalidate its downstream dependents while retaining independent completed work. Guidance reconciliation can update the task and existing subtask instructions together before work continues. Earlier results, files and sign-offs remain in history.

Tool permission requests remain pending while the native session is waiting. Stopping the session or service cancels an undelivered request; saved decisions are never replayed into a replacement session. Task access settings apply to the next attempt.

## Follow an attempt

Open an **In progress** task to follow the worker's activity. The worker should finish by submitting an outcome with its checks and limitations, or asking a blocking question. A final chat summary alone does not create a reviewable result.

If a worker ends normally without a submission or question, Flowfield gives it one reminder in the same session and checkout. This uses another model turn and retains the slot until cleanup completes. If it still does not report, work is preserved for inspection and explicit retry. Stopped or interrupted attempts are never restarted by this reminder.

Choose **Stop task** in the task header and confirm, or ask the Coordinator to stop it. This stops active Worker and Reviewer execution and moves the task to Backlog. Recorded work, files and history remain; questions from other waiting contributions are preserved. The control appears only when execution or cleanup is still active. **Retry worker** queues a fresh attempt; it respects pause, dependencies and capacity. Follow the displayed recovery action if native cleanup is uncertain.

## Read the task story

The feed groups definition changes, sources, questions, activity and results into initial work, corrections and follow-ups. Expand an event for its evidence; hover a timestamp for the exact time. Contribution work events name their assigned subtask. Feedback names its exact result. Earlier saved testing notes remain available as historical evidence. Worker and Reviewer activity keeps a bounded recent buffer; “Earlier activity is no longer retained” means older activity exceeded that buffer. Task events, results and submitted files are retained separately.

The task page stays at your reading position. Open worker or reviewer output to follow new entries inside that panel; scroll up to read earlier output and return to the bottom to follow again. Manual disclosure choices survive work-tab navigation. Numeric context occupancy and reported consumed tokens are separate measurements. The compact **Metrics** section shows lifetime reported Tokens, Cost, Duration and Corrections. The Corrections count includes Worker runs started to correct prior work, excluding retries and answer continuations. Hover, focus or tap Tokens, Cost or Duration for its Worker and Reviewer breakdown, or [explore workspace Metrics](/metrics) by period.

Current notices appear below task labels and above Definition. Use **View result** in the result notice to open the most recent saved result; earlier results remain in the feed. Follow a request or result link to answer, request changes, retry a failed review or approve code.
