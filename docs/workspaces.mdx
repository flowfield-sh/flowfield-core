title: Workspaces and projects
description: Organize related repositories around one conversation, roadmap and Inbox.

Create a workspace for projects that you want to plan together: an API, its application and its documentation, for example. It owns one Coordinator and shared work records; each project keeps its repository, tasks and code-delivery destination.

## Create and adopt

Choose **New workspace** from Home or the sidebar. Inside it, open **Projects → Add project → Choose directory**, select an existing repository and review the prefilled name, ID and task prefix. The three-letter prefix appears in task keys such as `API-1` and locks after the first task, including archived tasks.

The CLI uses the same registration:

```sh
flowfield workspace create "Harbor"
flowfield project init /absolute/path/catalog-api --workspace WORKSPACE_ID --prefix API
flowfield project init /absolute/path/reader-app --workspace WORKSPACE_ID --prefix RDR
```

Replace `WORKSPACE_ID` with the returned workspace ID. Registration writes project identity to `.flowfield/config.toml`; it starts neither a model nor the queue. Before managed implementation, establish a committed repository baseline and [validate its integration settings](/worker-setup).

Existing registrations stay in their current workspace. Moving projects between workspaces and merging conversations are not available. See [storage and upgrades](/storage#upgrades) for how earlier installations become workspaces.

## Find the work

The sidebar keeps workspace resources above **Work**, a compact list of milestones and standalone tasks. Tasks assigned to a milestone appear in its overview and on the Board. **All work** includes completed outcomes. The Work list scrolls independently, with queue controls below it. Use the workspace selector to switch conversations and drag the divider to resize the Coordinator.

| View | Use it to |
| --- | --- |
| Board | Follow task state and execution priorities. |
| Inbox | Answer questions, review results and resolve interventions. |
| Projects | Add repositories, open a project's board and reach its settings. |
| Milestones | Follow outcomes spanning several projects. |
| Documents | Maintain shared guidance and references. |
| Archive | Revisit work you set aside. |

Work lists **Needs attention**, **In progress**, then **Planned**, keeping a stable order within each group. A milestone moves into Needs attention when it or one of its tasks has an unresolved Inbox request. Completed work remains in **All work**. Home shows each workspace’s Inbox count.

Filter Board and Archive by project, milestone or label. The URL preserves those filters for reload, sharing and browser history. Task, milestone and document views stay beside the same Coordinator; on phones, switch between **Work** and **Coordinator**.

Sidebar and Coordinator links open or focus a resource tab. Links inside a tab stay there. Use the **Back** icon beside the view title to return within that resource. Drag resource tabs to reorder them, or focus a tab and press Alt+Left/Right; Inbox stays first. Selecting a tab restores its current page; reopening its root from the sidebar returns to that resource's starting page. **Inbox** stays pinned and clicking it returns to the request list. Use **Open in work tab** for comparison: it creates an independent tab at the exact page you are viewing, with no inherited history. Back becomes available after navigating within that tab. Cmd/Ctrl-click a link for a native browser tab. Browser Back and Forward restore the tab and page from that navigation entry. Setup and settings open in the working area beside the Coordinator. Small model selectors remain popovers.

Answers, review notes and document drafts stay bound to their original records when you switch or close resource tabs during the current browser session. Reloading or leaving the app warns about unsaved drafts. Only resource locations and layout preferences are stored in browser storage; draft contents stay in memory.

## Keep a shared roadmap

Describe the outcome to the Coordinator, which creates milestones and assigns tasks from different projects. Milestones appear under **Planned**, **In progress**, **Review** or **Complete**. A milestone with acceptance criteria reaches Complete after human acceptance and any configured promotion has been delivered; a lightweight group without delivery or criteria shows task completion. Its **Overview** leads with the outcome, current progress, acceptance criteria, available verification evidence and contributing tasks. **Details** retains saved description and criteria revisions; **Review** keeps verification reports, change requests and acceptance in one feed. Use **View tasks** or the task count on its card to open the filtered board.

Describe the intended outcome and, when useful, add **Acceptance criteria** for the complete experience. Keep each task's contribution in its own description. The task-based completion column reports progress; it does not verify those criteria.

The **Revisions** sidebar opens earlier descriptions and acceptance criteria at stable links. Ask the Coordinator to revise the outcome or criteria; the pane preserves each saved version. When the Coordinator prepares a task, Flowfield saves the current milestone details as context for that worker. The task's description defines its specific contribution to the outcome.

Later milestone edits leave prepared tasks intact and show **Milestone details changed** on affected unfinished work in the Board and Inbox. The task header links directly to the milestone revision used at preparation; its tooltip identifies that revision. Ask the Coordinator to assess whether the task needs updating. Existing installations retain the effective milestone details when upgraded; earlier unsaved revisions are unavailable.

### Verify and accept an outcome

Once the contributing tasks are delivered, ask the Coordinator to prepare whole-milestone verification. It prepares a report task with a checklist, the saved acceptance criteria and exact delivered contributions. The verifier runs through the normal queue and records evidence for each check. Failed checks, unverified outcomes or incomplete coverage require follow-up even when the verifier task itself is Done.

Passing verification moves the milestone into **Review** and adds one acceptance request to Inbox. Each verification report begins with **Details**: open **Limitations reported** when present, **Verification context** for the exact criteria revision and coverage notes, or **Tasks** for separate contribution and verification links. **Checks** and their evidence follow below. Status dots summarize the report and individual findings; hover or focus a dot for its status. Response controls and recovery hints sit at the bottom when action is needed. The same report and response controls are available in the milestone’s **Review** tab. For [owned milestone delivery](/tasks#assemble-and-review-a-milestone), use **Try milestone** and **Code changes** to inspect the combined candidate, then **Accept and promote** to deliver it to the project destination. Other milestones offer **Accept milestone** to record review of delivered versions. Enter feedback and **Request changes** when work needs correction. Neither action publishes a release.

The milestone pane retains verification and review history. Changes to acceptance criteria, contributing tasks or their results make pending evidence out of date. The completed verifier task remains a historical report; it is not automatically reopened when its inputs change. The previous report checked earlier versions; ask the Coordinator to review the changes and verify the updated milestone. Earlier acceptance remains a historical receipt and does not accept the changed outcome. Ask the Coordinator to address findings or review feedback and prepare another verification. Work in other repositories is unverified unless the verifier has deliberately prepared access and evidence.

After failed verification or a change request, send the Coordinator a message to review the findings and arrange the next step. The service continues scheduled workers, while the Coordinator resumes planning when you send a message. For corrections to delivered work, the Coordinator reopens the existing task as a draft in Backlog, then prepares and schedules the follow-up. Earlier results and approvals remain readable; reopening starts no worker. Corrected code needs a new exact result approved before another whole-milestone verification can use it. Earlier reports and review notes remain in the milestone feed.

Use [task dependencies](/tasks#dependencies) when one repository's work must finish before another can proceed. Milestones organize outcomes; dependencies connect individual tasks.

Labels are optional and shared across the workspace. Ask the Coordinator to maintain their names, colors, usage guidance and task assignments. A task can have several labels. Deleting a label removes current assignments while retaining its references in history.

## Configure at the right level

- **Workspace settings** owns its name, queue, worker defaults and shared capacity.
- **Project settings** owns repository identity, description, worker-document defaults and Integration: branch, setup, checks and local result previews.
- The **Coordinator input** owns its harness/model controls; task **Agent settings** can override the worker choice for subsequent attempts.

To open Project settings, select that project from Projects or filter the board to it. One project's setup blocker does not prevent ready work in other projects. See [worker setup](/worker-setup) and [workspace documents](/documents) for the remaining configuration.
