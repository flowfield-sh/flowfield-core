Open results from **Inbox**, **View result** in a task, or its feed. Each result contains the report, evidence and submitted files.

![An exact code result with its launcher, report and approval controls](/images/result-overview.png)

## Independent task review

Configure the **Task reviewer** in **Workspace settings → Reviewers**, or override it in **Task settings**. Review is enabled by default; subtasks share their parent’s review.

The Reviewer checks the result against its assignment and sources. Reviews share worker capacity and respect the queue.

The Reviewer can request clarification, corrections or focused verification, such as running the prepared candidate and collecting screenshots. Questions needing you appear in Inbox; saved answers continue review.

Checks that need a prepared candidate happen during review. The Reviewer must obtain that evidence before approving; implementation does not need to be repeated.

Visible UI changes and visual deliverables need visual evidence alongside functional checks.

Use **Stop task** to stop active review. Failed or stopped reviews need **Retry review**. If cleanup is uncertain, follow **Review rounds and diagnostics** before retrying.

After review, code needs your approval; complete files and reports finish automatically.

## Review an exact result

Read the report, checks and reviewer findings against the success criteria. Try representative inputs before deciding what ships.

During checks, the result shows the command, elapsed time and output. **Stop checks** stops execution and keeps the captured output.

Expand a command to read or download its log. Long logs retain their beginning and end. Successful checks can be reused for an unchanged candidate and configuration; reused checks are labeled.

**Run result** provides a launcher to try the candidate. Under **Details**, inspect supporting files, review evidence, guidance and code changes. See [worker setup](/worker-setup#try-a-result) for launcher configuration.

![Code changes and exact-result review beside the Coordinator](/images/code-review.png)

Choose **Request changes** for another pass, or **Approve and integrate** and confirm. Either can include testing feedback. Explicit approval of the exact result in the Coordinator conversation records the same decision.

Flowfield checks and delivers approved code to your local checkout. If local changes block delivery, resolve the reported problem and retry. Changed candidates need fresh approval.

## Find delivered outcomes

**Inbox → Delivered** lists completed outcomes by delivery time. Open a result to access code or retained files, or browse outputs across tasks in [Files](/files).

Delivery updates your local branch. Running, pushing and publishing need separate instructions; each repository has its own result and approval.

## Earlier results and follow-ups

If the destination advances, Flowfield prepares and checks the candidate against it. Conflicts can trigger a focused correction while the queue runs; the updated candidate needs fresh review and approval.

Completed results stay unchanged. If dependent work needs current validation of an earlier result, follow its **Check destination** link. Failed checks block the dependent work without undoing delivery.

Ask the Coordinator to create a new task for a new outcome, or reopen a task for a correction. Reopening retains earlier results, files and approvals; the new outcome needs fresh preparation and any required code approval.
