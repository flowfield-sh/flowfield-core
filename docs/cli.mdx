Workspace commands talk to your running local service. Commands inside a registered
project discover its identity from `.flowfield/config.toml`. Use `--project ID` when
working elsewhere, and `--help` at any command level for its options.

Commands show readable summaries, labeled details and explicit empty states by default.
Add `--json` only when you want machine-readable data for a script or diagnostic report.
JSON output is intentional when that flag is present; omit it for normal terminal use.

## Service and version

```sh
flowfield serve
flowfield --version
flowfield version --json
flowfield --help
```

`serve` opens the browser after startup in an interactive terminal. Use `serve --no-open`
to keep it closed. The service always prints its URL; browser-launch failure is nonfatal.

Global `--port` selects the service. `--data-dir` or `FLOWFIELD_DATA_DIR` selects storage;
`FLOWFIELD_PORT` sets the default port for the service and CLI. A command-line port
overrides it. For example:

```sh
flowfield --port 8770 serve
flowfield --port 8770 project list
```

## Updates

```sh
flowfield update status
flowfield update check
```

`status` reads the service's shared result, or the saved cache when the service is stopped.
`check` requests a manual check from the running service and waits briefly for the result.
Both accept `--json`; human update notices and errors use stderr. An unsuccessful manual
check exits with an error. These commands do not install software or start a service.
Offline status prints the command to start the service. Keep that terminal open while
using Flowfield; upgrading the package does not restart the service.
See [installation](/installation#update) for upgrade instructions and automatic checks.

## Storage and recovery

```sh
flowfield storage status
flowfield storage backups
flowfield storage restore BACKUP_ID --confirm
```

Storage commands run offline and accept `--json`. Status and backup listing do not
initialize or migrate the workspace. Recovery requires a stopped service and refuses
to discard writes made since the snapshot. See [local storage](/storage) for automatic
migrations, recovery limits and full backups.

## Projects and guidance

```sh
flowfield project init
flowfield project list
flowfield project show
flowfield project guidance preview
flowfield project guidance install
flowfield project guidance show
```

`project init /absolute/path` adopts an existing directory. Initial `--id`, `--name`
and `--prefix` override derived values. The three-letter task prefix locks after the first task.
The browser's **Add project → Choose directory** uses the same registration operation.
`project guidance export --part coordinator` prints the packaged skill without connecting
to a service. `project guidance remove` removes unchanged owned content and preserves local edits.

## Tasks and milestones

```sh
flowfield task list
flowfield task show APP-1
flowfield task activity APP-1
flowfield task relationships APP-1
flowfield task revisions APP-1
flowfield milestone list
flowfield milestone --help
```

Use stable task keys or IDs. Short task and milestone keys accept either case
(`fol-6` or `FOL-6`); internal IDs remain exact. The coordinator prepares task definitions through MCP;
CLI task operations expose the same workspace rules. Task dependencies and readiness
are checked by the service.

Every task starts with at least one outcome stage. `task create --title "…"` seeds a
single planned stage from the title. Use `--stages-file stages.json` to supply an array
of one to eight stages, each with an `id`, `title` and `outcome`.

`task edit` and `task prepare` also accept `--stages-file`, containing
`{"expected_revision": 1, "stages": [...], "reason": "Scope clarified"}`. Read the
current plan with `task stages APP-1 --json` or MCP `get_task_stages` first.
The plan and task change save together;
a stale revision rejects the whole change. Coordinator MCP calls can create or edit the
definition, stages and assignment preparation in one operation.

## Questions, execution and results

```sh
flowfield inbox list
flowfield inbox show QUESTION_ID
flowfield project workers show
flowfield project workers models
flowfield project workers run
flowfield project workers pause
flowfield task runs list
flowfield task runs show ATTEMPT_ID
flowfield task results list APP-1
flowfield task results show RESULT_ID
```

`project workers run` enables eligible Up next starts; `pause` leaves active workers
running. `task runs stop ATTEMPT_ID` targets one attempt. Inspect `task results review
--help` for exact-candidate approval and request-changes options; a result revision and
candidate commit are required. `task results retry-delivery --help` describes recovery
when approved code is blocked from reaching the checkout.

`task runs retry ATTEMPT_ID` returns stopped or failed work to Up next. It does not enable
a paused queue or bypass the worker limit.

Use `project workers models --project PROJECT_ID` to discover the project's native model
IDs and supported controls. `--refresh` reloads after native configuration or account
changes. `project workers configure --help` lists harness, model, effort, access mode
and parallel-worker settings. Omit effort only when that model offers no effort control.
Saving worker settings does not enable the queue.

Questions and replies preserve their task, attempt and result bindings. Answering does
not enable a paused queue; inspecting a result does not approve it.

## Project integration

```sh
flowfield project integration show
flowfield project integration configure --target main --check "make test"
```

Configure the target branch and trusted project checks to match your repository.
Repeat `--check` for multiple commands; `--setup` adds dependency setup. Your coordinator
can configure and validate richer environment and run-command settings through MCP.
Flowfield automatically uses the service host’s tools, credentials and native harness
configuration. Use `flowfield project workers models` to see access modes, then pass
`--mode MODE_ID` to `flowfield project workers configure` with the model and its supported
effort. A harness change clears inherited access; choose that harness's native access mode.
See [Worker setup and checks](/worker-setup) for configuration order and validation.

## Harness connections

```sh
flowfield integration connect codex
flowfield integration connect claude-code
flowfield integration status codex
flowfield integration disconnect codex
```

All three commands accept `codex` or `claude-code`. See
[standalone connections](/integrations/overview#standalone-conversations) for shared setup.

## Host harness settings

**Settings → Harnesses** detects native Codex, Claude Code and Pi installations. No separate
support install is needed. Optional path overrides and **Check saved setup** help resolve
missing executables or sign-in. Native accounts and advanced settings stay with the harness.

With the service running, read or change its native executable and configuration directory:

```sh
flowfield harness status codex
flowfield harness settings codex
flowfield harness configure codex --revision 1 \
  --executable /absolute/path/to/codex \
  --config-directory /absolute/path/to/native-config
```

Use the revision returned by settings. Each configure command replaces both overrides;
omit both paths to restore native defaults. Paths belong to the service host. The configuration
location is a directory (`CODEX_HOME` for Codex, `CLAUDE_CONFIG_DIR` for Claude,
`PI_CODING_AGENT_DIR` for Pi), not a settings
file. Saved overrides
take precedence over native environment variables; otherwise Flowfield detects the native
installation and configuration location. No native files, accounts or credentials change.
Service settings show the service host’s detected locations.

Host edits apply to future turns/attempts. Running work retains its saved registration and
observed launch locations. A changed native session location requires a fresh coordinator
session through the existing recovery flow; the saved chat remains. External native files
and account changes remain user-owned and are not frozen by Flowfield.

There is one configuration per supported harness kind. Use Codex, Claude Code, Pi or a mix;
the Coordinator and workers choose independently. Native installation, authentication and verified model access are separate facts. Detecting
paths starts no native process; explicit readiness checks use version/login-status commands
and never send a model prompt. Such checks cannot establish successful inference or billing.

Model and command discovery open disposable native sessions. They send no model prompt,
but native startup hooks can run. Model catalogs are scoped to the applicable project and
host registration, cached briefly, and limited to one active discovery per harness.
If discovery loses its native owner, Flowfield reserves that ownership across restart and
does not automatically retry. Read `harness settings KIND`, inspect and stop any
remaining native discovery on the service host, then confirm the exact discovery ID:

```sh
flowfield harness confirm-stopped codex --discovery DISCOVERY_ID
```

Settings also shows the discovery hold and offers the same explicit confirmation after
you inspect and stop remaining native work.

This confirmation clears the interrupted discovery hold. It starts no native process and
does not accept old discovery results; refresh the choices afterward. Native process
absence alone does not establish that background work has stopped.

## Automation

Add `--json` to data commands for structured output. Errors go to stderr with a nonzero
exit status. Versioned edits require the current revision; do not overwrite newer intent
from an outdated read. Paged reads return cursors and truncation metadata: follow them
rather than treating the first page as complete history.

Read older saved coordinator exchanges with `flowfield project coordinator-history
--project PROJECT --json`. It returns newest first; pass `next_cursor` as `--before`.
Read an exchange's retained text with `flowfield project coordinator-text TURN
--project PROJECT --field human --revision REVISION --json`, or use `--field coordinator`
for public reply prose. Follow `next_offset` as `--offset` while keeping the revision;
restart the read if output changed. Marked omissions are not recoverable, and these
reads do not reconstruct native tool history or transfer permissions or approval.
