Use Codex, Claude Code, or both. Install and sign in to the harness on the machine
running Flowfield, then choose it for your Coordinator and workers. Integration support
ships with Flowfield; there is no separate bridge to install.

These native integrations are in development source; published 0.2.1 predates them.
Pi is next and is not selectable yet.

## Built-in Coordinator and workers

1. Start Flowfield and add your existing project.
2. Choose a harness and model for each role during project creation or in project settings.
3. Configure and validate [worker delivery](/worker-setup) when you're ready to run tasks.

**Settings → Harnesses** detects native installations. Override executable/configuration
paths only when detection needs help. Accounts and advanced native settings stay with
the harness. **Check saved setup** checks version and sign-in without sending a prompt;
**Not checked** does not block a working conversation.

Opening a project preloads its configured models; reconnecting after a service restart
checks them again. Other choices load when their selector opens. Loading controls stay
disabled. Discovery sends no model prompt, although native startup hooks can run.

| Capability | Codex | Claude Code |
| --- | --- | --- |
| Coordinator and managed workers | Yes | Yes |
| Automatic Flowfield tools and model discovery | Yes | Yes |
| Independent choices per role and task | Yes | Yes |
| Native continuation and Stop | Yes | Yes |
| Standalone connect/status/disconnect | Yes | Yes |
| Model and access controls | Native advertised choices | Native advertised choices |

Built-in roles receive scoped Flowfield tools automatically. Workers use separate
checkouts and task-bound instructions. Native permission choices never approve delivery
of code to your project. See [Codex](/integrations/codex) and
[Claude Code](/integrations/claude-code) for native controls and limitations.

## Standalone conversations

To keep the Coordinator conversation in your own coding harness, run the same commands
with `codex` or `claude-code`. Flowfield must already be running:

```sh
flowfield integration connect claude-code
flowfield integration status claude-code
```

Connect verifies Flowfield and saves a user-scoped MCP connection through the native CLI.
It uses the current terminal's native account/configuration, preserves other servers and
refuses conflicting names. Repeating connect is harmless. Status checks configuration,
service reachability and tool discovery; it does not prove that an open conversation has
loaded the connection. Native project overrides or organization policy can still affect it.

From your [adopted project](/getting-started#add-your-project), install shared guidance:

```sh
flowfield project guidance preview
flowfield project guidance install
```

This adds `.agents/skills/flowfield-coordinator/SKILL.md` and a short `AGENTS.md` reference,
preserving existing instructions. Review and commit these files under your project's rules.
Start a fresh conversation in the project, ask it to read that guidance, and then read your
Flowfield board. Existing `CLAUDE.md` and other native instructions remain intact.

For another service port or connection name, use the same options for every operation:

```sh
flowfield --port 8770 integration connect claude-code --name flowfield-local
flowfield --port 8770 integration status claude-code --name flowfield-local
flowfield --port 8770 integration disconnect claude-code --name flowfield-local
```

Disconnect removes only that matching user connection. Restart the harness to unload its
tools. Projects, conversations and tasks remain saved. Built-in roles need none of these
standalone commands.
