---
title: ACP and MCP
description: How Flowfield communicates with coding agents and exposes project tools.
---

Flowfield uses two complementary protocols:

| Protocol | Connection | Purpose |
| --- | --- | --- |
| Agent Client Protocol (ACP) | Flowfield → coding harness | Send messages, receive activity, select settings and handle tool permission requests. |
| Model Context Protocol (MCP) | Coding harness → Flowfield | Read project context, maintain tasks and report work through scoped tools. |

## ACP: running the conversation

[ACP](https://agentclientprotocol.com/get-started/introduction) standardizes communication
between coding agents and their client applications. Flowfield acts as the client for
the Coordinator and managed task workers, using a local subprocess connection.

Codex and Claude Code adapters connect through installed ACP bridges. They discover native
model capabilities, apply supported settings, stream public text/tool activity and handle
native permission requests. Compatible coordinator settings resume saved native sessions;
workers run scoped task attempts in their own workspaces.

Flowfield provides the coordinator commands `/status`, `/compact`, `/mcp` and `/skills` when
the Codex harness advertises them. Claude commands are not exposed. See
[Coordinator](/coordinator) for the controls and session behavior.

Install the selected bridge with `flowfield harness install codex` or
`flowfield harness install claude-code`; install and authenticate the native harness
separately. No Node/Bun runtime is required. Harness switches use a fresh native session
and a bounded Flowfield handoff, retaining public history and older scoped source reads.
Native session files, private reasoning and permission grants are not converted.

## MCP: working with Flowfield

[MCP](https://modelcontextprotocol.io/docs/getting-started/intro) connects AI applications
to tools and context. Flowfield exposes project and task operations through its local service.
The tools use the same revisions, saved answers and exact-result approval rules as the GUI
and CLI. MCP discovery supplies their names, descriptions and input schemas.

For a standalone coding conversation, connect the harness to
`http://127.0.0.1:8765/mcp/` and install the project guidance. Follow the
[Codex setup instructions](/integrations/codex#connect-a-standalone-coordinator).
Use your configured service port if it differs from the default.

Built-in coordinator and worker sessions receive service-managed, scoped connections
automatically. Their tools are limited to the relevant project or task, and their grants
end with the attempt. No separate standalone connection is needed for built-in chat.

Coordinators can page older saved exchanges with `get_coordinator_history`, then use
its `text_sources` with `get_text` to read relevant human messages and public replies
in bounded chunks. Follow `next_cursor` as `before` and echo the returned text revision;
if output changes, restart the read. Marked omissions remain unavailable. These reads
exclude native session IDs, tool history and private reasoning. Task workers keep their
run-bound context and do not receive these project conversation tools.

The project skill explains the workflow; MCP supplies the operations. Neither a tool call
nor a harness permission decision grants approval to deliver a worker's code result.
